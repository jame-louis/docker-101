## 开场（约 2 分钟）

各位同学，大家好。今天这节课我们来学习 Docker 技术体系中非常关键的一环——Dockerfile。

先问大家一个问题：如果让你把开发环境原封不动地交给另一位同事，你会怎么做？写一份安装文档？让对方照着文档一步步操作？做过的人都知道，这种方式十有八九会出岔子——版本不对、依赖缺失、系统差异，总有一款坑等着你。

Dockerfile 就是来解决这个问题的。它把"如何从零搭出一个运行环境"这件事**代码化**了：一个纯文本文件，逐条写明每一步操作，Docker 照着它自动构建出镜像。只要 Dockerfile 在，任何人、任何机器上构建出来的环境都一模一样。所以请大家记住这句话：**要像重视你的代码一样重视 Dockerfile，并把它纳入版本控制。**

今天的课程分三部分：第一，Dockerfile 的基本结构，这是难点；第二，常用指令，这是重点；第三，动手实践，编写 Dockerfile 并用 docker build 构建镜像。

---

## 第一部分：基本结构（约 8 分钟）

### 什么是 Dockerfile

我们先明确概念。Dockerfile 有两个用途：一是**对应用的描述**——它清晰记录了应用本身和它的全部依赖；二是**指导 Docker 完成容器化**——把应用打包成镜像。它实现了开发和部署的无缝切换。

关于文件本身有两条硬性规定：第一，文件名必须是大写 D 的 `Dockerfile`，不能写成 dockerfile 或 Docker file；第二，它通常放在**构建上下文**的根目录。这里引出第一个概念——构建上下文，就是包含应用文件的目录，执行 `docker build` 时，Docker 会把整个目录发给守护进程，COPY 指令只能取这个范围内的文件。

书写规则很简单，大家看这张表：井号开头是注释；每行一条指令；指令不区分大小写，但**惯例全大写**，这样能和参数区分开；执行顺序是从上到下逐条执行。

### 四段式结构

一个典型的 Dockerfile 分四段：**基础镜像、元信息、构建过程、启动配置**。我们用这个 Python 应用的例子来看——`FROM` 指定从哪个镜像出发，它是唯一必须放在第一位的指令；`LABEL` 写元信息；中间一连串 `WORKDIR`、`COPY`、`RUN` 是构建过程；最后 `EXPOSE` 和 `CMD` 告诉容器启动时干什么。

### 难点：镜像分层与缓存

接下来是今天的第一个难点——**镜像分层机制**。

请大家记住三句话。第一：**每条向镜像里增添文件或程序的指令，都会生成一个只读层**，镜像就是这些层的堆叠。FROM、RUN、COPY 会建层，而 EXPOSE、WORKDIR、ENV 这类只告诉 Docker"怎么构建、怎么运行"的指令，只记录元数据，不产生新层。

第二：**层是可以缓存的**。构建时如果某条指令和它之前的指令都没变，Docker 直接复用缓存，跳过执行。

第三，也是最容易踩坑的：**缓存失效会向后传导**。一旦某一层缓存没命中，它后面的所有层全部重建，哪怕它们本身没变。

理解了这三句话，两条编写原则就水到渠成了。**原则一：按变化频率从低到高排列指令。**大家看这个对比——如果把 `COPY . .` 放在 `pip install` 前面，业务代码改一行，依赖层的缓存就失效了，每次构建都要重装依赖，非常慢。正确的做法是先 COPY 依赖清单 requirements.txt，装完依赖，最后才 COPY 业务代码。**原则二：能合并的 RUN 尽量合并。**每条 RUN 就是一层，三条 RUN 就是三层，而且中间层还会残留 apt 缓存垃圾；用 `&&` 串成一条，一层搞定，顺手清理缓存，镜像更小。

## 第二部分：常用指令（约 12 分钟）

这部分是今天的重点。我们按使用频率来，前五个指令必须熟练掌握。

### FROM 与 RUN

`FROM` 指定基础镜像，必须是第一条有效指令。选基础镜像的建议是：优先官方镜像、优先小体积变体，比如 alpine、slim。还有一个特例 `FROM scratch`——空镜像，这个我们先埋个伏笔，实践环节会详细讲。另外，一个 Dockerfile 可以写多个 FROM，用于多阶段构建，后面有专门例子。

`RUN` 在**构建镜像时**执行命令，会创建新层。它有两种写法：shell 形式和 exec 形式。这里特别提醒：`RUN` 是构建时执行，`CMD` 是容器启动时执行，考试和面试都爱考这个区别。

### COPY 与 ADD

`COPY` 把构建上下文里的文件复制进镜像，会创建新层。它会检查文件的校验和，内容变了缓存就失效。`ADD` 是增强版，多了两个能力：自动解压本地 tar 包、支持 URL 下载。但最佳实践很明确：**优先用 COPY**，语义明确；只有确实需要自动解压时才用 ADD。

### CMD 与 ENTRYPOINT（重点中的难点）

这是指令部分最容易混淆的一对，请重点听。

`CMD` 是**默认**启动命令——"默认"两个字是关键，它可以被 `docker run` 后面的参数直接覆盖。`ENTRYPOINT` 是**固定**入口，`docker run` 的参数不会替换它，而是**追加**给它当参数。

举个例子：镜像的 CMD 是 `python app.py`，你执行 `docker run 镜像 echo hi`，实际跑的是 `echo hi`，CMD 被换掉了；而如果入口是 ENTRYPOINT，同样这条命令实际跑的是 `python app.py echo hi`。

两者还能配合使用，看这个经典写法：`ENTRYPOINT ["ping"]` 加 `CMD ["localhost"]`。直接 run 就是 ping localhost；run 时带上 8.8.8.8，CMD 被替换，变成 ping 8.8.8.8。入口固定、参数可换，非常优雅。

补充两条规则：一个 Dockerfile 里多个 CMD 只有最后一个生效；推荐统一用 exec 形式，也就是 JSON 数组写法，这样信号能正确传递，容器能正常响应停止信号——shell 形式下 PID 1 是 sh，容易收不到停止信号。

### 其余指令

剩下的指令我们快速过一遍。`EXPOSE` 只是**声明**端口，是文档性质的元数据，真正的端口映射要靠 `docker run -p`。`ENV` 和 `ARG` 都定义变量，区别在于：`ENV` 构建期和运行期都在，容器里还能读到；`ARG` 只在构建期存在，构建完就消失，还能用 `--build-arg` 覆盖。`WORKDIR` 设置工作目录，只记录元数据——注意千万别用 `RUN cd /app` 代替，因为每条 RUN 在独立的层里执行，cd 对后面的指令无效。

其他指令看这张速查表：LABEL 写元数据、USER 切换运行用户、VOLUME 声明挂载点、HEALTHCHECK 做健康检查、ONBUILD 给子镜像设触发器。MAINTAINER 已废弃，用 LABEL 代替。

## 第三部分：实践教学（约 15 分钟）

### 官方 hello-world 剖析

进入动手环节。先看一个现成的、也是 Docker 世界最著名的镜像——官方 hello-world。它在 Docker Hub 和 GitHub 上都有官方页面，仓库地址是 github.com/docker-library/hello-world。

它的 Dockerfile 只有三行，请看大屏幕：`FROM scratch`——还记得我们埋的伏笔吗？scratch 就是完全为空的基础镜像；`COPY hello /`——把一个提前编译好的 C 可执行文件拷进镜像；`CMD ["/hello"]`——容器启动就执行它，打印出那段 "Hello from Docker!" 然后退出。

这里顺便解答一个大家常问的问题：为什么 hello-world 容器跑完就退出？因为镜像里没有 shell、什么都没有，唯一的进程 hello 打印完就结束了，容器自然就停了。

### 拓展思考：空镜像为什么能跑程序？

顺着这个问题往深挖一层：**空的 scratch 镜像，凭什么能运行 hello 这个可执行文件？**这是理解"容器不是虚拟机"的关键。

第一层原因：**容器共享宿主机的内核**。很多人误以为镜像就是一个迷你操作系统，错了。虚拟机要带完整的 Guest OS 和自己的内核，所以镜像以 GB 计；而容器本质上是宿主机上的一个普通进程，只是用 namespace 做了隔离、用 cgroups 做了资源限制。所有容器共用宿主机正在运行的那个 Linux 内核，内核根本不在镜像里。所以 scratch 的"空"，空的是用户空间，系统调用直接找宿主机内核。这也解释了为什么 hello-world 只有约 13KB，以及为什么 Linux 镜像不能直接跑在 Windows 上——内核对不上。

第二层原因：**hello 是静态编译的**。普通动态链接的程序启动时需要动态加载器和一堆 .so 共享库，scratch 里啥都没有，动态程序进去启动就报错。而 hello 用 `gcc -static` 编译，C 库代码全部打包进了二进制内部，自包含，内核直接加载就能跑。课堂上可以演示一下：`ldd hello` 输出 "not a dynamic executable"，再对比 `ldd /bin/ls` 列出一串动态库，反差一目了然。

### 实战：Flask 应用五步构建

现在轮到大家动手了。我们把一个 Flask Web 应用打包成镜像，五步走。

第一步准备文件：app.py、requirements.txt、Dockerfile 三件套。第二步写 Dockerfile——注意这里的写法正是前面原则的落地：先 COPY requirements.txt 装依赖，后 COPY 业务代码，最大化利用缓存。第三步构建：`docker build -t flask-demo:1.0 .`，`-t` 打标签，末尾的点指定构建上下文。第四步验证：`docker images` 看镜像，`docker run -d -p 5000:5000` 起容器，`curl localhost:5000` 看到 "Hello, Docker!" 就成功了。

第五步是今天的演示亮点——**亲身体验缓存**。改一行 app.py，重新 build，大家观察输出：pip install 那一步显示 CACHED，秒级完成。这就是"依赖层在前、代码层在后"带来的真实收益。

时间允许的话，再看两个进阶例子：Alpine 版的 Node.js 应用，完整走一遍八步构建输出；以及多阶段构建——Go 程序第一阶段用 1GB 的 SDK 编译，第二阶段 FROM scratch 只拷贝编译产物，最终镜像从 1GB 缩到几 MB。第二阶段敢用 scratch，前提正是我们刚讲的"静态编译 + 共享内核"。

## 附：docker build 常用参数（答疑备用）

| 参数 | 作用 |
|---|---|
| `-t, --tag` | 指定镜像名称和标签，格式 `name:tag` |
| `-f` | 指定 Dockerfile 路径和名称 |
| `--no-cache` | 构建时不使用缓存 |
| `--build-arg` | 设置构建时变量 |
| `-q, --quiet` | 静默模式，只输出镜像 ID |
| `-m, --memory` | 设置构建内存上限 |
