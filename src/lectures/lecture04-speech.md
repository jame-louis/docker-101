## 开场（约 2 分钟）

各位同学，大家好。经过前面几讲的铺垫，我们已经知道了容器是什么、Dockerfile 怎么写。但大家有没有想过一个问题——Dockerfile 构建出来的那个"东西"，到底是什么？你 `docker run` 起来的容器，又是从哪来的？

答案就在今天这节课的核心——**镜像（Image）**。可以说，镜像理解了，Docker 的整个技术体系就打通了一半。

今天的课分三块：第一，镜像到底是什么，以及它和容器那对最容易混淆的关系；第二，镜像的命名、标签和仓库；第三，也是最核心的，镜像的本质——分层。最后我们用两个动手实践，亲手拉一个镜像、解剖它，再亲手把容器变成一个镜像，把今天讲的概念全部串起来。

---

## 第一部分：镜像的定义（约 8 分钟）

### 什么是镜像

先给镜像下一个定义：**镜像是一个只读包（read-only package），里面装着一个应用要跑起来所需的全部内容。**请特别注意"只读"这两个字——它一旦被创建出来，就再也不允许被修改。

一个镜像里装了什么？装四样东西。第一是**应用程序本体**——你的代码、脚本、二进制程序；第二是**应用依赖**——库文件、运行时，比如 Python 或 Node，还有配置文件；第三是**操作系统构造的最小集合**——busybox、必要的库文件，是运行所必需的那一小撮组件；第四是**元数据**——端口、环境变量、默认启动命令这些描述信息。

用一句话概括：**镜像 = 把"能跑应用的那台环境"打包成一个静态文件。**拿走它，到任何地方都能把应用跑起来。

### 镜像通常很小

这里要纠正很多初学者最根深蒂固的一个误解：以为"镜像 = 一台操作系统"。差距其实非常大。就拿官方的 Alpine Linux 镜像来说，整个下载下来只有**约 7MB**。

为什么能这么小？因为它三样东西都没有。第一，**没有完整的多用户 shell 环境**；第二，**没有包管理器**；第三，也是最重要的——**不包含内核**。容器和宿主机**共享同一个内核**，内核根本不在镜像里。所以镜像才能做到几十甚至几 MB。Windows 镜像因为工作方式不同，动辄就是 GB 级。

### 镜像与容器：必须分清

初学最容易混淆的就是"镜像"和"容器"。记住一个类比就好：**镜像是图纸，容器是照图纸盖出来的房子。**

图纸是只读的，改图纸不会影响已经盖好的房子，而且一份图纸能盖出无数栋房子。容器也一样——一个镜像能启动一个、两个、甚至一百个彼此独立、互不干扰的容器。

再补一个更贴代码的类比：镜像之于容器，就像**类之于对象、程序之于进程**。镜像是"构建时"的静态模板，容器是"运行时"的可写实例。这层直觉一定要建立起来，后面很多概念都从这派生。

## 第二部分：镜像名、标签与仓库（约 5 分钟）

### 为什么需要名字和标签

全世界镜像成千上万，我们得有一套命名的规则来区分它们。规则很简单，格式是：**镜像名:标签**。

镜像名用来区分不同的项目或应用，标签用来区分同一个项目内的不同版本。比如 `ubuntu:latest`、`ubuntu:v1`、`ubuntu:v2`，它们是同一份底层数据挂上的不同"铭牌"。

这里要破除一个常见误解：**latest 不代表最新。** 它只是一个默认的标签名而已。你不写标签，Docker 就默认帮你挂 `latest`，但人家新版本推出时未必会更新这个标签。

### 镜像仓库与 Docker Hub

镜像存在哪？存在一个叫**镜像仓库（Registry）**的服务上，作用类似 App Store。里面按项目名组织出来的集合叫 Repository，比如 `alpine`、`python`。Docker 官方的公共仓库叫 **Docker Hub**，是全世界最大的镜像仓库。

拉取时完整写法其实有前缀：`[registry/]repository[:tag]`——比如完整写出来是 `registry.hub.docker.com/python:3.12-slim`，但我们平时省略 registry，默认就是从 Docker Hub 拉。企业中通常会在内网搭私有仓库（如 Harbor、Nexus），分发更快也更安全。

## 第三部分：镜像的本质——分层（约 10 分钟，重点）

### 分层结构

现在进入今天的核心。大家可能会想：镜像是不是一堆文件糊在一起的一团东西？**不是。** 镜像是由**一组松耦合的只读层（layer）堆叠**而成的——每一层包含一个或多个文件，一层一层往上叠，最后叠成一个完整的镜像。

最底层通常是你选的基础镜像，比如 Alpine；上面每一层，都是某条指令加进来的。后面讲 Dockerfile 时你会反复看到 `RUN`、`COPY` 就是在"加一层"。`docker history` 命令能一五一十地看到这一层层。

### 层是可以共享的

分层带来的第一个巨大好处是**共享**。因为每一层都是独立、只读、可复用的，所以如果你的镜像基于 Alpine，那么 Alpine 的那几层，所有基于它的镜像都能共用，磁盘上只存一份。

这就带来连锁的三个好处：**省磁盘**——共享层不重复存；**省带宽**——下载新镜像时只拉取没命中的层；**加速构建**——构建时缓存能命中不变的部分。记住一句话：Docker 拉镜像，传的是差异层，不是整个镜像。

### 为什么分层这么重要

把这四个好处再敲一遍重点：省磁盘、省带宽、加速构建、便于分发。这也是下一讲"优化 Dockerfile"的伏笔——**把容易变化的文件放靠后的层，把稳定不变的内容放靠前的层**，让缓存尽量命中。大家先把这句话记在心里，下节课会落地。

### 进阶：写时复制

最后讲分层带来的一个精妙机制——**写时复制（Copy-on-Write，简称 COW）**。镜像明明是只读的，那容器怎么还能往里写文件？

答案在这：启动容器时，Docker 会在只读镜像层之上，额外叠加一个**可写的容器层**。容器读文件，就读镜像底层的只读副本；容器要写文件，就先把那个文件**复制**到容器层，再在容器层上写。所以叫"写时复制"。

关键点来了：**容器删除后，可写层跟着一起销毁，底层镜像毫发无损。** 这既保证了镜像的只读性，又让多个容器各自隔离、又共享底层。

## 第四部分：常用镜像命令（约 7 分钟）

这部分是今天的重点，命令都实打实要考。我把它们按使用频率分成三层。

### 核心命令：pull / images / push / rmi

第一层是**四大核心命令**，熟练到闭眼能打。

`docker pull` 拉取镜像，从仓库下载到本机。它频繁用，但不是必需——因为 `docker run` 时如果本机没有，会自动先 pull。

`docker images`（等价 `docker image ls`）查看本机所有镜像，列出 REPOSITORY、TAG、IMAGE ID、SIZE 四列。

`docker push` 把我们本地镜像推送到仓库，供别人拉取或异地部署。推送到 Docker Hub 前，通常要先把镜像 tag 成自己的用户名，还得 `docker login` 先登录。

`docker rmi` 删除镜像是四个字——注意 `rm` 管容器、`rmi` 管镜像。它只能删掉没有被任何容器使用的镜像，有容器引用就删不动，得先删容器。

### 打包与传输：tag / history / inspect / save / load

第二层是镜像的"身份证"和传输工具。

`docker tag` 给镜像加标签。注意它的本质——**只是给同一个镜像 ID 增加一个别名/引用，不复制任何数据。** 所以改它、删它，都不会动原镜像。常用于给发布版本命名、改名推仓库、区分 dev/staging/prod 环境。

`docker history` 查看镜像由哪些层构成，每一行就是一层，直观体现"分层"。`docker inspect` 返回完整 JSON 元数据，包括标签、架构、环境变量，常配 `--format` 过滤字段。

`docker save` / `docker load` 是离线传输利器。`save -o` 把镜像导出成单个 tar 文件，拷到没网的机器上再 `load -i` 恢复。注意它保留完整的分层结构，比 `export/import` 语义更完整。

### 了解即可：commit / search

第三层了解即可。`docker commit` 把某个容器的当前可写层打包成新镜像。它是快速快照，但不被推荐为正式构建方式——可读性、可复现性都差。正式项目一定用 Dockerfile。今天实践二我们会用它，就是为了体验"从无到有"的过程。

还有 `docker search` 在 Docker Hub 搜公共镜像，`docker buildx` 做多架构构建，`docker system prune` 一键清理垃圾。这些按需掌握。

## 第五部分：实战一——拉取并解剖一个镜像（约 5 分钟）

现在动手。第一个实践，目标是亲手拉一个镜→运行它→解剖它，直观感受"分层"。

**第一步**，`docker pull hello-world`，屏幕会分步显示 `Pulling fs layer` 再到 `Pull complete`，这就是分层在真实世界中跑起来的证据。

**第二步**，`docker run --rm hello-world`，会打印一段 "Hello from Docker!" 然后容器退出。`--rm` 表示退出后自动删除容器。

**第三步**，拉一个真实的 `alpine:3.20`。注意看输出里每个 `Pull complete` 对应一层——alpine 是由多层构成的。

**第四步**，`docker history alpine:3.20`。你会看到：一行是 `CMD`（元数据，0B），行是 `ADD` 出来的基础层（7.38MB）。**每一行就是一层**，前面讲的理论现在看得清清楚楚。

**第五步**，`docker inspect alpine:3.20`，返回一大段 JSON。再 `--format '{{.Architecture}}'` 只取一字段。翻翻看 `ExposedPorts`、`Env` 这些字段长什么样。

**第六步**，再拉一个同样基于 Alpine 的 `nginx:alpine`，`docker images` 对比，体会"共享底层"带来的体积优势。

## 第六部分：实战二——从容器创建你的第一个镜像（约 6 分钟）

第二个实践，我们要用 `docker commit` 亲手把一个容器变成镜像，把 tag → save → rmi → load 这整条镜像生命周期走一遍。再强调一遍：这是为了把"镜像从无到有"讲直观，正式项目请用 Dockerfile。

**第一步**，启动交互式容器：`docker run -it --name myubuntu ubuntu:22.04 /bin/bash`，进入后看到 `root@<容器ID>:/#` 提示符。

**第二步**，在容器里做点修改：`apt-get update && apt-get install -y curl`，再装 vim，然后 `exit`。注意——此刻 curl、vim 装进了容器的**可写层**，但底层 ubuntu 镜像本身没变，回想一下写时复制。

**第三步**，`docker commit myubuntu myubuntu:with-tools`，输出一行新的镜像 ID。修改被定格成了新镜像。

**第四步**，验证：`docker images` 多出了新镜像；`docker history` 能看到在 ubuntu 底层之上叠加了新增的层。

**第五步**，`docker tag myubuntu:with-tools jamelouis/myubuntu:v1`，再 `docker images`——同一个 IMAGE ID 挂着好几个名字，这就是"加别名"的直观体现。

**第六步**，`docker save -o myubuntu.tar jamelouis/myubuntu:v1`，导出成离线文件。

**第七步**，删除再导入：先 `docker rm myubuntu` 删容器，再 `docker rmi` 删两个镜像名，`docker images` 确认删光了；最后 `docker load -i myubuntu.tar`，镜像又回来了。这一去一回，你等于亲手备份、恢复了一次镜像。

**第八步（可选）**，`docker login` 后 `docker push jamelouis/myubuntu:v1`，体验推送。企业里通常推到 Harbor 这类私有仓库。

## 结尾（约 2 分钟）

最后我们总结。今天内容很硬核，用一张表带走全部要点。

**本质**：镜像是只读包，含应用、依赖、最小化 OS、元数据，**不含内核**，与宿主机共享内核，所以通常很小，Alpine 才 7MB。

**镜像 vs 容器**：镜像是构建时的只读模板，容器是运行时的可写实例，一个镜像能启动无数个容器——图纸和房子的关系。

**命名**：`镜像名:标签`，标签默认 latest 但 latest≠最新；仓库默认 Docker Hub。

**分层**：镜像由多层只读层堆叠，层可跨镜像共享，省磁盘省带宽加速构建；容器的可写层靠写时复制，容器删除镜像无损。

**命令**：核心是 pull / images / push / rmi；按需靠 tag / history / inspect / save / load / commit。

**实践**：实践一 pull + run + history + inspect 体会分层；实践二 commit + tag + save + rmi + load 走通镜像生命周期。

这是一张非常重要的记忆地图。从下节课开始，我们要从"有图"进阶到"画图"——用 Dockerfile 自动化、可复现地构建镜像，让今天埋下的"分层""缓存"伏笔逐个兑现。今天的课就到这里，谢谢大家！
